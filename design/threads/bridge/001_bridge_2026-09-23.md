# 001 - bridge to mzLibRust - 2026-09-23 - Every wire verb now has one YAML spec, and mzLibRust's rustdoc renders from it: act as if you had already agreed

**Decision (the maintainer's, 2026-09-23): adopted, effective now.** Please reply to confirm, and
from today act as if you had already agreed. This is the first message on this thread. The *bridge*
is the umbrella project above pyMzLib, mzLibRust and mzLibR. It owns the language-neutral wire
contract that all three bindings project.

## What changed

A large batch of mzLib work is about to be projected into all three bindings: 26 merged mzLib PRs
since 1.0.591. They include MetaMorpheus protein-group and peptide tables, mzIdentML, SDRF sample
informativeness and age parsing, and Ensembl and GO annotation. The documentation for it must be
**world class** and **the same in Python, Rust and R**.

An audit on 2026-09-23 found the three bindings already drifting apart:

- `lib.rs` says 31 file types where the bridge says 32.
- The README heading still says "Four capabilities" over five modules.
- All 10 doctests are `no_run`.
- No binding runs a single example.
- There is no per-verb contract anywhere; the wire shape exists only as C# code and recorded fixtures.

So the facts about each wire verb now live in exactly one place: one YAML file per verb in the
bridge (`design/verbs/<module>.<verb>.yaml`). A spec records:

- params with **units** and valid ranges, and defaults
- result fields with type, **unit**, **nullable and what null means**
- error kinds (usage / service_unavailable / correctness) and when each happens
- caveats
- the mzLib symbols wrapped, at the pin
- DOIs for the science
- fixture-backed examples in all three languages
- `since` per binding

A checker validates each spec against the bridge's verb switch and the recorded fixtures. The pilot
is `readers read-spectra`. **Your binding keeps its idiom**: names, the `_with` + options-struct
shape, typed results, and prose. The spec owns the facts; where a binding's docs disagree with the
spec, the binding is wrong.

## Asks

**SPEC-1 · A projected verb cites its spec.** Every verb you project from now on names its spec
file in the PR. Record the verb's `bindings.rust` spelling (for example
`mzlib::readers::read_spectra_with` + `SpectraOptions`) and its `since.mzlibrust` version, and send
both back to the bridge.

**SPEC-2 · Render and lint rustdoc from the spec.** Use the shared reference-page order: summary,
wraps, params, returns, errors, caveats, executed example, performance, see also (including the
Python and R spellings), references, since.

- Generate the params, returns and errors tables from the spec and include them with
  `#[doc = include_str!(...)]`.
- Add a test that reads the specs and fails when a param or field has no doc on the options or
  result struct, or when its doc has no unit.
- Add `RUSTDOCFLAGS="-D warnings" cargo doc --no-deps` to CI, so broken intra-doc links fail.

**SPEC-3 · Doctests run.** Change `no_run` to runnable doctests against a fixture-replay stub bridge
(`MZLIB_BRIDGE` pointing at a stub that returns the spec's named fixture). They share the fixtures
pyMzLib and mzLibR use. Add `[package.metadata.docs.rs]`, and start a Keep-a-Changelog
`CHANGELOG.md` whose entries use the spec's `since` versions.

**SPEC-4 · Close the existing parity gaps and stale text before the batch.**

- `pride search` and `quant median-polish` are on the wire and in Python, but not in Rust.
- `lib.rs` says 31 formats; that becomes 36 after the next repin (4 new file types in mzLib master).
- `live_readers.rs:65` expects "14 of 31".
- The README heading says "Four capabilities".
- Three sites still warn about mzLib#1111, which #1155 fixed inside the current pin.
